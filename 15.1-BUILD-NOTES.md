### Camera enumerated 0 — binderized provider crash (regression, fixed) — 2026-06-23

This consolidated ROM first shipped/started the **binderized** camera HAL service
`android.hardware.camera.provider@2.4-service` (a vendor process). On `camera_device_open`
it `SIGABRT`ed: `camera.qcom.so` → `SensorManager::getInstanceForPackage` →
`assertStateLocked()` `LOG_ALWAYS_FATAL` (a vendor process can't reach the *system*
`sensorservice`), so the framework saw 0 cameras / crash-on-open. But treble is **off**, so
the HAL1 is meant to run **passthrough** inside cameraserver/mediaserver (a system process,
where SensorManager works). Fix: `disabled` added to
`hardware/interfaces/camera/provider/2.4/default/android.hardware.camera.provider@2.4-service.rc`
so the binderized service never starts and the framework uses the passthrough `@2.4-impl`.
Verified from a clean boot: provider service not running, `Number of camera devices: 2`,
`camera_device_open ... rc 0` (both cams open, no abort). The running ROM was also live-patched
(`/system/vendor/etc/init/...rc` is on the system partition) so it's fixed without a rebuild.
Live preview still hits the separate parked blob blocker (`dequeue_buffer: no free buffer`).

### Bluetooth MAC provisioning (genuine Sony OUI) — 2026-06-23

Source-only since the `22bdf02c` ROM; live-verified on-device. Bluetooth worked but
advertised a placeholder address `08:00:00:1E:E2:48` (non-Sony OUI) — `btnvtool`
(`config_bt_addr`) generates it on first boot because nothing seeds the BT BD_ADDR from
the factory TA partition. Wi-Fi, by contrast, gets its genuine Sony MAC
`44:d4:e0:46:08:ff` (OUI `44:d4:e0`) from the factory-provisioned
`/persist/WCNSS_qcom_wlan_nv.bin`.

Fix: new `device/sony/nicki/rootdir/etc/init.qcom.bt_mac.sh` derives the BT address from
the factory Wi-Fi MAC (Wi-Fi − 1 in the low octet, the Sony convention) and writes it to
`/persist/.bt_nv.bin` in QC NV format (`01 00 06` + addr LSB-first), then `exec`s the stock
`btnvtool -O`. Guarded by an OUI-match check (idempotent; never clobbers a genuine factory
address), and clears the stale `/data/misc/bluedroid/bt_config.conf` cache on the one
migration boot so bluedroid repopulates from the controller. Wired by repurposing the
`config_bt_addr` service in `init.qcom.rc` to run the script (guarantees provisioning
finishes before btnvtool/bluedroid read the NV). Copy rule in `product/bluetooth.mk`.
Verified end-to-end across a real reboot: adapter now reports `44:D4:E0:46:08:FE`.
Note: the running device's `/persist/.bt_nv.bin` is already permanently fixed; the
`init.qcom.rc` wiring lives in the ramdisk, so it only takes effect for fresh installs /
NV resets after a `boot.img` rebuild.

### Baseband version "Unknown" — 2026-06-23

Settings → About phone showed Baseband version "Unknown". Two causes: (1) the closed modem
answers `RIL_REQUEST_BASEBAND_VERSION` with `GENERIC_FAILURE` (`[BASEBAND_VERSION error 2]`
in the radio log), so the framework never sets `gsm.version.baseband` — and it only queries
once at radio-on (an airplane-mode toggle doesn't re-trigger it); (2) the existing
`bbset` service script `rootdir/etc/init.qcom.baseband.sh` was a leftover from an **MSM8930**
device — it grepped `/dev/block/bootdevice/by-name/modem` (nicki has no such by-name link)
for build id `M8930B-AAAATAZM` (nicki is MSM8227), so it set nothing.

Fix: rewrote the script to recover the genuine modem RTOS build string embedded in the
firmware image — `strings /firmware/image/modem.b02 | grep 'BLAST Kernel ver'` →
`02.04.02.02.09` — and `setprop gsm.version.baseband`. The `bbset` service (init.target.rc,
root / `qti_init_shell`, late_start) already runs this `/system/etc` script, so the fix
needs only the `/system` change (no boot.img rebuild). Verified: About phone now shows
`02.04.02.02.09`.

nicki has only ~880 MB usable RAM but ran with the framework's full-RAM profile (memory
status "moderate", ~28 MB free). Enabled the standard Android Go low-RAM tuning (adapted
from `build/make/target/product/go_defaults_common.mk`, NOT inherited wholesale — that

### Notification LED dead — boot-order race — 2026-06-23

The RGB notification LED never lit. Chain: framework LightsService → passthrough
`light@2.0` HAL (in system_server; treble off) → CM "Xperia Lights Wrapper"
(`lights.msm8960.so`) → Sony vendor blob (`lights.vendor.msm8960.so`) → `/data/LED_deamon.{rd,wd}`
FIFOs → `led_deamon` → kernel `fih_led` driver (RGB via PMIC LPG, `/sys/class/led/fih_led/control`).

Symptom: `LightsService: Light requested not available on this device. 2` (id 2 =
NOTIFICATIONS). Root cause = **boot-order race**: the passthrough HAL builds its light map
**once** at system_server init (~14–15 s, zygote at 14.1 s) by calling the vendor blob's
`open()` for each light; the LED lights need `led_deamon`'s FIFOs, but `led-deamon` (class
main) didn't start until **~19.1 s** — so `open(notifications/battery/attention)` failed
(dead FIFO → EINVAL → `vendor light open fail`) and stayed `LIGHT_NOT_SUPPORTED` for the
whole session. (keyboard/buttons `-22` are expected — nicki has no such lights.)

**UPDATE — the real root causes (LED now works, user-confirmed):** the led_deamon boot-order
theory was a partial red herring (the `not available. 2` was the *buttons* light, id 2, which
correctly has no hardware). Two independent bugs actually broke the LED:

1. **HAL drove the LED through the fragile led_deamon path.** Rewrote
   `device/sony/nicki/liblights/lights.cpp` to drive the kernel `fih_led` "control" node
   **directly** for notifications/battery/attention (RGB brightness + blink via text commands
   `<cmd> <led_id> <params>\n`, led 0=red/1=green/2=blue), bypassing led_deamon + the vendor
   blob + /data FIFOs entirely. Key gotcha: the kernel parser needs a **trailing newline** or
   it logs "Can't get parameter" and ignores the write. backlight stays direct-LCD; only
   buttons still forwards to the blob. The LED control node is `system:system 0600` (init.rc
   chowns it) so the in-process light HAL in system_server can write it. (lights.msm8960.so —
   /system lib, no boot.img needed.)

2. **The framework didn't believe nicki had an LED.** `LightsCapabilities` reads
   `config_deviceLightCapabilities` from `org.lineageos.platform` (lineage-sdk), default **8**
   (LIGHTS_PULSATING_LED only). The device override lived in `overlay/vendor/cmsdk/cm/res/` —
   a dead CM-era path (`vendor/cmsdk` is absent), so it applied to nothing and the framework
   thought there was no notification/battery LED, never calling the HAL. Fix: new
   `overlay/lineage-sdk/lineage/res/res/values/config.xml` with **75** =
   1 (RGB notif) + 2 (RGB batt) + 8 (pulse) + **64 (LIGHTS_BATTERY_LED — "has battery LED",
   what LineageBatteryLights.isSupported() actually gates on; the old "11" convention predates
   this bit)**. Rebuilds `org.lineageos.platform-res.apk` (verified `d=0x4b` on device).

(The `init.target.rc` `start led-deamon` in post-fs-data is now moot but harmless — kept.)
The previous start-order paragraph above is superseded.

### Known issue: ~10 kHz mic whine (hardware coupling) — 2026-06-23

Microphone recordings/calls have a high-pitched whine. Characterized by recording the raw
codec TX (pushed `tinycap` + manual `tinymix` handset-mic path: SLIM TX1 MUX=DEC1,
DEC1 MUX=ADC1) and FFT'ing it: a sharp **~10037 Hz tone + 20 kHz 2nd harmonic**. Frequency is
rock-stable across screen bright (10 kHz peak ~185k) / dim (~161k) / **off (~124k)** — so the
display/backlight is only ~1/3 of it and **~2/3 persists with the screen fully off**. It is
"analog-messy" (10037 Hz is not a clean divisor of 48 kHz) with a single harmonic → signature
of a **fixed oscillator coupling into the analog mic** (PMIC/DC-DC/charging or codec bias),
NOT a digital/sample-rate artifact. All audio config (mixer_paths.xml, audio_platform_info.xml,
audio_policy_configuration.xml, audio_effects.conf) is **byte-identical to the working 14.1**,
so it's not a 15.1 config regression and almost certainly exists on 14.1 too.

Not fixable in software (electrical source). The only software lever is a WCD9304 IIR
band-stop (~10 kHz notch) on the mic TX path in mixer_paths.xml — strongly attenuates the
whine, inaudible cost for calls/voice (band-limited), minor high-freq loss for music.
Deferred by user choice; revisit if it becomes a priority. (tinymix controls confirm TX1 HPF
is already On at 4 Hz; IIR1 bands are unused/Off and available for the notch.)

### Extra performance tuning — 2026-06-23

Beyond the low-RAM/Go layer (`product/lowram.mk`, MALLOC_SVELTE, lz4 zRAM), surveyed the
runtime and applied a few safe wins (live-verified, then sourced):
- **I/O scheduler `bfq` → `deadline`** (`init.target.rc on boot`): bfq is the kernel default
  but CPU-heavy; deadline is lighter on the dual-A5 with predictable eMMC latency.
- **vm.swappiness 60 → 100** (`init.target.rc on boot`): lean on the cheap lz4 zRAM so more
  file pages stay cached (fewer slow eMMC re-reads) on this RAM-starved device.
- **Disabled `perfprofd`** (`disabled` in `system/extras/perfprofd/perfprofd.rc`): a
  perf-profiling telemetry daemon with no user value whose periodic simpleperf collection
  causes hitches on the weak CPU.
Surveyed-and-left-alone: GPU is TZ-managed (no devfreq governor to tune); logd is already
64 KB; SELinux-permissive audit overhead is currently ~0 (not a constant drain); interactive
CPU governor + defaults are fine. Optional UX tweak (not applied): animation scales 0.5x
(`settings put global {window,transition}_animation_scale / animator_duration_scale 0.5`) for
snappier perceived UI. Init changes are ramdisk → need the boot.img; applied live for now.

### Browser video playback slow (software VP9) — 2026-06-24

Web video (YouTube etc.) in Jelly/WebView was slow. Cause: MSM8227/Adreno-305 has HW decode
only for H.264/MPEG/VC1/DivX (`OMX.qcom.video.decoder.*`); VP8/VP9/HEVC are software-only
(`OMX.google.*`). The stock `media_codecs_google_video_le.xml` advertised the SW VP8/VP9
decoders, so YouTube served VP9 and Chromium **software-decoded it in the renderer** (Jelly
pinned at ~148% CPU on the dual-A5, ~0% idle — verified: no `OMX.qcom` decoder, no mediaserver
activity, pure in-renderer decode). Note `ro.config.low_ram=true` did NOT make Chromium 138
avoid VP9, and `--enable-accelerated-video-decode` couldn't help (no HW VP9 decoder exists).
Fix: device-local `configs/media_codecs_google_video_le.xml` with the SW-only VP8/VP9/HEVC
**decoders removed** (kept SW H.264/MPEG4/H263 + all encoders), wired via `qcom-media.mk`
(was copying the framework file verbatim). Web players then fall back to H.264 → the Qualcomm
HW decoder. Verified after reboot: VP8/VP9 gone from `cmd media.codec list` (0); YouTube
instantiates `OMX.qcom.video.decoder.avc` (HW, on the Q6 DSP); **Jelly CPU 148% → 78% (58% idle)**
— video decode offloaded off the CPU. /system-only change (no boot.img); live-pushed + in source.

## 2. The fixes (in the order the build hit them)

All paths under `src/`. Most are 2018-isms: the device tree was written for
2018 LineageOS infrastructure, and the 2026 branch drifted (split-CIL sepolicy,
mandatory savedefconfig, strict aapt2 overlays, CM→Lineage rename, etc.).

### Kernel / build glue

1. **`BOARD_KERNEL_IMAGE_NAME not defined`** — 15.1's inline kernel build
   (`vendor/lineage/build/tasks/kernel.mk`) requires the output image name.
   `device/sony/nicki/board/kernel.mk`: added
   `BOARD_KERNEL_IMAGE_NAME := zImage` (3.4/ARM → zImage).
   *(The "Building Kernel Config / savedefconfig" step looked like it failed in
   filtered logs but actually succeeds — with `-j`, ninja just lets it finish
   before stopping on whatever real failure ran in parallel.)*

### Vendor init (`init_nicki`) — Oreo C++ API migration

2. **`'selinux/label.h' file not found`** (via `system/core/init/util.h`) —
   `device/sony/nicki/init/Android.mk`: added
   `external/selinux/libselinux/include` to `LOCAL_C_INCLUDES` and `libselinux`
   to `LOCAL_STATIC_LIBRARIES`.
3. **`use of undeclared identifier 'property_set' / 'ERROR'`** —
   Oreo moved init's API into `android::init` and logging severities into
   `android::base`. `init_nicki.cpp`: replaced `using android::base::GetProperty;`
   with `using namespace android::base; using namespace android::init;`.
4. **`ERROR` still undeclared** — none of the included headers pulled in the
   logging macros. `init_nicki.cpp`: added `#include <android-base/logging.h>`.

### SELinux policy (the bulk of the work)

The device sepolicy was Nougat-era and self-contained; the 8.1 platform policy +
modern qcom sepolicy conflict with it in many ways.

5. **`syntax error at token 'qmux_socket'`** (netmgrd.te) — the device's macro
   files were disabled (renamed `*.txt`) and qcom sepolicy wasn't wired in.
   `device/sony/nicki/board/selinux.mk`: added
   `include device/qcom/sepolicy/sepolicy.mk` (provides `qmux_socket`,
   `msm_sock_ipc_ioctls`, `qmuxd_socket`, BOARD_SEPOLICY_VERS, etc.).
6. **`syntax error at token 'allow-thermal-engine'`** — typo.
   `thermal-engine.te`: `allow-thermal-engine` → `allow thermal-engine`.
7. **`Duplicate declaration of type` qmuxd_socket** — device declared it as
   `dev_type`, qcom as `file_type` (conflict). `device.te`: removed
   `type qmuxd_socket, dev_type;` (let qcom's win).
8. **`Duplicate declaration` netmgrd/qmuxd** — qcom common now owns those domains
   completely. Deleted the redundant `device/sony/nicki/sepolicy/netmgrd.te` and
   `qmuxd.te` (would also have duplicated the `init_daemon_domain()` macro rules).
9. **`unknown class sock`** (mediaserver.te) — `sock` is not a class.
   Merged `allow mediaserver socket_device:sock_file write;` +
   `... :sock ioctl;` into `allow mediaserver socket_device:sock_file { write ioctl };`.
10. **`unknown type sysfs_rmtfs`** (rmt.te, a macro-arg type qcom no longer
    provides) — `file.te`: declared `type sysfs_rmtfs, sysfs_type, fs_type;`.
    Also dropped the stale `shared_log_device` grant from `rmt.te` (that
    Nougat-era diag node type no longer exists).
11. **`neverallowxperm ... domain:socket_class_set ioctl { 0 }`** — the 8.1
    platform requires every domain granted `socket ioctl` to whitelist its
    ioctls. Three sony domains (init, ta_qmi_service, rmt) granted
    `self:socket ioctl` with no `allowxperm`. Added to each:
    `allowxperm <domain> self:socket ioctl msm_sock_ipc_ioctls;`
    (matching `thermal-engine` and qcom's `rild`). *Only the monolithic
    `sepolicy.recovery` enforces plat neverallows; the split-CIL `nonplat`
    passed — that's why this surfaced late.*
12. **`Multiple … specifications` in file_contexts** — the device `file_contexts`
    duplicated entries qcom common/msm8960 now provide (and conflicted on
    `/dev/msm_rotator`: device `video_device` vs qcom `graphics_device`).
    Removed all device entries that overlap the qcom/lineage `file_contexts`
    (the 7 dev nodes + 5 `qmux_*` sockets) from
    `device/sony/nicki/sepolicy/file_contexts`; qcom's labels win.

### Framework resource overlay

13. **`resource integer/config_deviceHardwareWakeKeys does not override an
    existing resource`** — 8.1 aapt2 requires static-overlay resources to exist
    in the base. This Lineage resource isn't in the 15.1 base framework (the
    maintainer had already commented out its siblings `config_deviceHardwareKeys`,
    `config_intrusiveBatteryLed`, `config_ui_blur_enabled` but missed this one).
    `overlay/frameworks/base/core/res/res/values/config.xml`: commented out
    `config_deviceHardwareWakeKeys`.

### Prebuilt blob

14. **webview `package.apk` fails / `ZipException`** — `git-lfs` synced
    `external/chromium-webview/prebuilt/arm/webview.apk` as a 133-byte pointer.
    In the container: `cd .../prebuilt/arm && git lfs install --local && git lfs pull`
    (nicki is ARM32 → only the `arm` prebuilt matters). Same issue/fix as 14.1.

### CM → Lineage Java rename

15. **`The import org.cyanogenmod.internal cannot be resolved` / `FileUtils
    cannot be resolved`** (org.lineageos.hardware lib, 98%) — two device HAL Java

    `device/sony/nicki/cmhw/org/cyanogenmod/hardware/{VibratorHW,DisplayColorCalibration}.java`:
    `org.cyanogenmod` → `org.lineageos` (package + `FileUtils` import). The

## 4. Boot result: it doesn't

Flashed our `recovery.img` to the **boot** partition (Sony's S1 bootloader blocks
`fastboot flash FOTAKernel`/`recovery` with "Command not allowed", and
`fastboot boot recovery.img` returns OKAY but doesn't actually run a RAM image —
both are Sony bootloader limitations; flashing recovery to `boot` is the nicki
way in). Result: **stuck at the Sony logo, no recovery UI.**

Ruled out (so the cause is the kernel itself, not packaging):
- **Boot image format is correct** — header v0 (right for this bootloader),
  page_size 4096, kernel_addr 0x80208000, ramdisk_addr 0x82200000,
  tags_addr 0x80200100, ramdisk_offset 0x02000000. Matches nicki's layout.
- **Toolchain matches 14.1** — kernel built with `arm-linux-androideabi-4.9`
  (`arm-linux-androidkernel-` prefix), the same GCC the booting 14.1 uses.
- Kernel: droncheg `kernel/sony/msm8x27` **master** @ 85a6d4b — the kernel the
  device-tree author themselves paired with this los-15.1 tree —
  config `lineageos_nicki_defconfig`.

Stuck at the Sony logo = the kernel dies before display init, i.e. before any
recovery UI could appear; recovery shares the boot kernel, so neither boots.

**Conclusion:** this is the boot wall. The 2018 tree compiles but the kernel
never boots — almost certainly why the port was frozen. Going further is a
**kernel bring-up project, not a build fix**: you'd need a **UART/serial console**
(MSM8x27 exposes a debug UART; on these Sonys often via the magic-cable / headset
detection resistor or test points) to capture the early panic, since nothing is
written to `last_kmsg` when it dies this early. That, plus likely kernel patching,
is open-ended with no guarantee on a 2013 phone. **Stopped here; 14.1 remains the
daily driver.**

### Un-bricking after the failed boot

Because recovery was flashed to `boot`, normal boot is gone. Restore the working
kernel: power off fully → hold **Volume-Up while plugging USB** (blue LED =
fastboot) → `fastboot flash boot <working-14.1-boot.img>` → `fastboot reboot`.
(14.1 boot.img: `~/android/lineage-14.1/src/out/target/product/nicki/boot.img`.)

## 3. Flashing (the nicki way — recovery goes on `boot`)

The Sony S1 bootloader only allows flashing **`boot`** (FOTAKernel/recovery are
"Command not allowed"; `fastboot boot` is a no-op). So the recovery goes on the
boot partition; the ROM install then writes the real boot.img over it.

1. `fastboot flash boot recovery.img` → `fastboot reboot` (boots into recovery)
2. Factory reset / **format data** (8.1 layout differs from 7.1)
3. `adb sideload lineage-15.1-*-nicki.zip` (+ ARM 8.1 GApps if wanted) —
   the device-compat assert passes because our recovery reports `ro.product.device=nicki`
4. Reboot.

**As of 2026-06-18 step 1 already fails** — the recovery kernel doesn't boot
(stuck at Sony logo). See §4. Until the kernel boots, the ROM can't be installed.
