# LineageOS 16.0 (Android 9 / Pie) bring-up notes — Sony Xperia M (`nicki`)

Forward-port of the [15.1 port](README.md) to Android 9. The kernel and graphics
blobs carry over from 15.1; this documents the Pie-specific work. Blow-by-blow,
newest-relevant first.

## Build walls (in order hit & cleared)

1. **Product discovery** — Pie dropped `add_lunch_combo`; added
   `device/sony/nicki/AndroidProducts.mk` (`PRODUCT_MAKEFILES := lineage_nicki:$(LOCAL_DIR)/lineage.mk`).
2. **Audio kernel headers** — `hardware/qcom/audio-caf/msm8960/hal/Android.mk`
   re-set `LOCAL_HEADER_LIBRARIES :=` in the same module block, clobbering
   `generated_kernel_headers` → `sound/msmcal-hwdep.h` not found. Changed the 2nd
   assignment to `+=`. (`patches/android_hardware_qcom_audio-caf_msm8960.patch`)
3. **sepolicy** — removed Pie-dropped types (`camera_socket`, `mpdecision`),
   fixed 8 neverallow build-asserts (`sysfs_type`→`fs_type` for the sysfs led
   nodes, `data_file_type`/`core_data_file_type` on /data types, isolated_app
   sysfs, dac_override). (in the device tree)
4. **kernel `O_TMPFILE`** — the 3.4 asm-generic `fcntl.h` shadowed bionic's;
   backported `O_TMPFILE`. (kernel repo)
5. **webview** — LFS pointer apks; pulled the real prebuilts.

## Runtime blockers (in order)

- **Recovery "wipe data" no-op** — `bootable/recovery/roots.cpp` aborted
  `format_volume()` when the crypto `key_loc` (`/persist/footer`) was unreachable
  in recovery. Made that non-fatal so `mke2fs` still runs.
  (`patches/android_bootable_recovery.patch`)
- **No adb in recovery / booted** — Pie adbd is FunctionFS-only; nicki's 3.4
  kernel has the legacy in-kernel `/dev/android_adb` gadget. Ported the 15.1
  runtime-probe adbd patch. (`patches/android_system_core.patch`)
- **Files app crashes / no internal storage** — Android 9 stripped the userspace
  FUSE path from `/system/bin/sdcard`, leaving it sdcardfs-only; nicki's 3.4
  kernel has no sdcardfs/esdfs (only FUSE) → the daemon aborts (`failed to
  sdcardfs_setup`), the emulated volume never mounts (`sm list-volumes` =
  `emulated unmountable`), and DocumentsUI finds no `primary` root → bounces to
  launcher (looks like a crash). Restored Oreo's FUSE-capable `sdcard` daemon
  (`fuse.cpp`/`fuse.h` + `should_use_sdcardfs()` auto-fallback), and added `i` to
  its `getopt` string since Pie's vold passes `-i` (unshared_obb). Pie's vold
  still execs the daemon and waits for the FUSE mount, so no kernel change is
  needed (`CONFIG_FUSE_FS=y`). (`patches/android_system_core.patch`)
- **Camera enumerates 0 devices** — the Sony `camera.msm8960` blob `dlopen`-fails
  on `_ZN7android16CameraParameters11KEY_SONY_ISE`. The device header
  `CameraParametersExtra.h` (defining the `KEY_SONY_*`/`KEY_GPS_*_REF` statics)
  was forward-ported but not wired: added the `CAMERA_PARAMETERS_EXTRA_C/_H`
  hooks to `CameraParameters.{h,cpp}` and the `-include` to `libcamera_client`
  `cflags` → the symbols are defined → the blob loads → 2 cameras enumerate.
  (`patches/android_frameworks_av.patch`)
- **Camera open / live preview / capture-without-crash** — ported the four 15.1
  HAL1 `CameraDevice.cpp` fixes: (1) zero-extend the 32-bit blob gralloc usage
  (`(BufferUsage)(uint32_t)usage`) so Gralloc2 doesn't reject
  `0xffffffff…`; (2) gralloc0-lock dequeued preview buffers so the blob sees a
  mapped `->base`; (3) local-id fallback when `registerMemory` transport fails;
  (4) single-open `sGetMemory` cookie-recovery so the snapshot stream's bogus
  cookie doesn't SIGSEGV `takePicture`. Enumerate + open + **live preview** work;
  photo **save** is still parked (see Known issues).
  (`patches/android_hardware_interfaces.patch`)
- **Boot stall — missing `vendor.lineage.power@1.0` HAL** — manifest declared it
  but the service was disabled → framework blocked forever in
  `ILineagePower::getService()`. Re-enabled the service (device tree).
- **Black display (SurfaceFlinger back-pressure)** — the msm8960
  HWC1-via-`HWC2On1Adapter` reports `PresentFenceIsNotReliable`; the present
  fence never signals → `SurfaceFlinger::onMessageReceived(INVALIDATE)` sees
  `frameMissed` forever and skips compositing after the first frame. Set
  `debug.sf.disable_backpressure=1` (`product/display.mk`).
- **Popup / notification-shade / scroll freeze (~10 s)** — with back-pressure
  disabled, SF's own framebuffer output starved: `FramebufferSurface::onFrameCommitted()`
  attached the unreliable present fence as the FB buffer's release fence, so the
  buffer never freed and SF blocked in `msm_fb_pan_idle`/`sync_fence_wait` on any
  sustained buffer cycling (`DequeueBufferDuration=9.9 s`). Static surfaces
  (keyguard) hid it. Fix: skip that fence (`NO_FENCE`) when the HWC reports
  `PresentFenceIsNotReliable`; the client-target acquire fence (a real GPU fence)
  is kept for client-composited layers. 99th-pct frame 4950 ms → 129 ms.
  (`patches/android_frameworks_native.patch`)
- **Wi-Fi HAL couldn't bring wlan0 up** — `android.hardware.wifi@1.0-service`
  (`user wifi`, `capabilities NET_ADMIN`) ran with `CapEff=0`: the kernel's
  ambient-cap backport zeroed `pA'` on a non-root exec (`commoncap.c`
  intersected ambient with the freshly file-recomputed, empty permitted before
  folding it in). Fixed in the kernel repo (bound ambient by inheritable only).
- **Wi-Fi supplicant configs not seeded** — Pie no longer seeds
  `/data/misc/wifi/{wpa_supplicant,p2p_supplicant}.conf`; wpa_supplicant exited on
  the missing `-c` file → `ISupplicant` never registered. Added an
  `on post-fs-data` seed from the vendor template (`rootdir/init.target.rc`).
- **Wi-Fi signal bars missing** — wificond's `GetStationInfo()` returned false
  when `NL80211_RATE_INFO_BITRATE32` was absent; the old prima driver only
  reports the legacy 16-bit `NL80211_RATE_INFO_BITRATE` → every signal poll was
  "invalid" → RSSI stuck at −127. Added the 16-bit fallback and made bitrate
  non-fatal. (`patches/android_system_connectivity_wificond.patch`)
- **rild crash-loop** — a stale `libril.so` blob (52 KB, no `ril_service_name`)
  in `system/lib` shadowed the built CAF `libril.so` (236 KB). Removed the copy
  from `nicki-vendor.mk`. **Gotcha:** removing a `PRODUCT_COPY_FILES` entry does
  **not** delete the already-installed file from `out/` — `rm` it (or
  `make installclean`) or the OTA keeps shipping the stale artifact.
  (`patches/vendor_sony_nicki.patch`)
- **Bluetooth HAL crash-loop** — passthrough `@1.0-impl` aborts on Pie
  (in-process `linkToDeath`). Switched to the binderized
  `android.hardware.bluetooth@1.0-service` + `hwbinder` manifest entry, and
  published the controller BD_ADDR to `persist.service.bdroid.bdaddr` from
  `init.qcom.bt_mac.sh` (the HAL only reads the ASCII prop, not the binary NV).
- **Bluetooth radio** — the adapter stuck at `BLE_TURNING_ON` /
  `BLE_START_TIMEOUT` forever with a placeholder BD_ADDR. Two causes: (1) the
  Pie `libbt-vendor` blob sets the **vendor-namespaced** prop
  `vendor.bluetooth.hciattach=true`, but `init.qcom.rc` only triggered the
  `hci_attach` service on the legacy `bluetooth.hciattach` — so `hci_qcomm_init`
  never ran, the SMD transport never attached, and the controller never got the
  BD_ADDR. Added an `on property:vendor.bluetooth.hciattach=…` trigger (device
  tree). (2) the WCN SMD transport bring-up takes ~5.5 s per enable cycle, but
  the framework's `BLE_START_TIMEOUT_DELAY` was 4 s — the stack reached
  `btif_enable_bluetooth_evt status 0` at ~+5.2 s but the framework had already
  torn it down and looped. Bumped `BLE_START_TIMEOUT_DELAY` +
  `BREDR_START_TIMEOUT_DELAY` to 8000 ms
  (`patches/android_packages_apps_Bluetooth.patch`). Verified: enable→**ON** &
  stable, auto-enables on boot with the real Sony MAC `44:D4:E0:46:08:FE`, and
  discovery finds nearby devices. (Aside: `cmd bluetooth_manager enable` is not
  implemented — use `svc bluetooth enable`. Non-fatal:
  `timer_create(CLOCK_BOOTTIME_ALARM)` ENOTSUPP on the 3.4 kernel; bt_osi falls
  back.)
- **HW video decode** — `OMX.qcom.video.decoder.avc` (and all HW video) failed:
  `ACodec: Failed to allocate buffers ... dequeueBuffer failed: Out of memory`.
  Not OOM — the allocator returns `BAD_VALUE`: Pie's `Gralloc2` (frameworks/native
  libui) `validateBufferDescriptorInfo()` rejects buffers whose usage has bits
  outside the standard valid mask, and the msm8960 decoder's tiled-NV12 output
  buffers set QCOM-private usage bits `PRIVATE_UNCACHED` (1<<25) and
  `PRIVATE_IOMMU_HEAP` (1<<30) that LineageOS's QCOM config doesn't whitelist.
  Oreo used the non-Treble direct-gralloc path (no such HIDL validation), which is
  why HW decode works on 15.1 with the same blob. Fixed by whitelisting the QCOM
  private usage range via `TARGET_ADDITIONAL_GRALLOC_10_USAGE_BITS` in
  `board/qcom-display.mk` (fed to libui's `-DADDNL_GRALLOC_10_USAGE_BITS`; must use
  `1ULL` — `1<<31` on signed int is `-Werror` UB). Verified: HW-accelerated H.264
  video (local files + browser MP4) plays clean. This also makes the pre-existing
  "strip SW VP8/VP9 so browsers serve HW H.264" media_codecs fix actually
  effective. (WebM/VP8/VP9 HW decode is impossible — the vidc 720p core has no
  VP8/VP9 block; only H.264/MPEG4/H263/MPEG2/VC1/DivX. WebM stays SW-only.)
- **Auto-rotate / accelerometer** — the BMA250 accel never streamed (`enable`=0,
  no events) so auto-rotate didn't work, though the sensor is registered and
  `WindowOrientationListener` is subscribed. `bsthal` (the Bosch accel/mag HAL
  inside the binderized `android.hardware.sensors@1.0-service`) writes the accel
  `enable` sysfs node directly, but that node is `root:input` 0660 and the
  service's init `.rc` had `group system wakelock` without `input` (gid 1004) →
  the enable write got EACCES (silent under permissive SELinux) → accel never
  powered on. (Prox/light work because they go via `sensord`, which has the input
  group.) Fixed by adding `input` to the group line in
  `android.hardware.sensors@1.0-service.rc` (`patches/android_hardware_interfaces.patch`).
  Verified: accel streams live gravity, auto-rotate works. (Note: init only
  re-reads the `.rc` on boot, not on `ctl.restart`.)
- **Display flicker / tearing** — a per-layer flicker, worst on slow scroll (15.1
  is clean, so a Pie regression). Long-standing, and previously mis-root-caused as
  "the present fence never signals on Pie, unfixable". The actual chain: this
  HWC1-via-HWC2On1Adapter reports `PresentFenceIsNotReliable`, and SF's handling of
  that had *three* interacting problems. (1) SF fed the unreliable present fence to
  `DispSync` (`postComposition`), which corrupted the vsync model and made SF call
  `disableHardwareVsync()`. (2) With the panel vsync IRQ disarmed, the **mdp4 retire
  fence stopped advancing** — and that retire fence is exactly what backs
  `getLayerReleaseFence()`. (3) So an earlier bring-up pass, seeing per-layer release
  fences that never signalled (producers blocking ~10 s in `dequeueBuffer`,
  `DequeueBufferDuration`=9.9 s, animating surfaces hard-freezing), forced
  `Fence::NO_FENCE` in `postFramebuffer` — releasing every layer buffer immediately.
  That is the flicker: the producer overwrites a buffer the MDP overlay is still
  scanning out. The fence wasn't unfixable, it was starved by (1)/(2), and the
  "every attempt to honour the fence freezes the device" observation was a symptom
  of fixing (3) without (1)+(2). Fixed as one coordinated change in
  `SurfaceFlinger.cpp` (`patches/android_frameworks_native.patch`), all three
  guarded on `PresentFenceIsNotReliable` so other HWCs are untouched: don't feed the
  unreliable present fence to DispSync; keep HW vsync permanently enabled
  (`onVsyncReceived`) so the retire fence advances; and honour the per-layer release
  fence again in `postFramebuffer`. The fence then signals ~2–3 refreshes late and
  the triple-buffered app producers absorb that without starving. Verified on device:
  flicker gone, no freeze under sustained scrolling (no Davey, `Missed Vsync: 0`), MDP
  composition still `mdpCount 3 fbCount 0`. `debug.sf.disable_backpressure=1` and
  `debug.mdpcomp.idletime=-1` are both still required/kept.
- **NFC crash-loop** — `com.android.nfc` SIGABRT'd on every startup:
  `phHciNfc_Response_Timeout` → `phOsalNfc_RaiseException` → `abort`. The log gave
  it away: `NFC-HCI: Could not open /vendor/firmware/libpn544_fw.so` →
  `Firmware image not available`. `libnfc`'s `FW_PATH` was hardcoded to
  `/vendor/firmware/libpn544_fw.so`, but the app linker namespace for
  `com.android.nfc` (which `dlopen`s libnfc) permits `/system/vendor/lib` and NOT
  `/system/vendor/firmware`, so the firmware open failed, the FW download was
  skipped, and HCI init then timed out and raised a fatal exception. The blob is
  actually installed at `/vendor/lib/libpn544_fw.so` (== `/system/vendor/lib`,
  non-Treble). Fixed by pointing `FW_PATH` there (`external/libnfc-nxp`,
  `patches/android_external_libnfc-nxp.patch`) — same fix 15.1 carried, which was
  not ported forward. Verified on device: NFC enables, the PN544 reports its
  capabilities (`FW = b10122, HW = 620003`, `NCI_Version: 16`), `mState=on`, zero
  crashes. (Tag read-write not physically tested, but the chip now completes HCI
  init instead of timing out.)

## Known-broken / TODO

- **Camera photo save** — enumerate + open + live preview work, but capture
  hangs at save. Corrected diagnosis (2026-07-04, was wrong before): the
  snapshot frame **is** delivered and the JPEG encode **starts**
  (`mm-still-omx: jpegEncode : X`), then the OMX/jpege blob hard-deadlocks —
  every mm-jpeg thread parks in `FUTEX_WAIT` forever, no CPU, no `/dev/gemini0`,
  a lost-wakeup inside the closed `libmmstillomx`/`libmmjpeg` (byte-identical to
  15.1 which captures fine → Pie-runtime trigger, unpatchable from outside).
  Separately, a real kernel bug was found + fixed: `msm_poll()` returned
  `-EINVAL` (→ `POLLERR`) for a stopped snapshot stream fd, so the HAL poll
  thread busy-spun a core; `vb2_poll()` also returns `POLLERR` on an empty
  `queued_list`. Fixed in the kernel (`msm: camera: msm_poll: stop returning
  POLLERR for idle stream fds`, on branch `lineage-15.1-nicki`) — the spin is
  gone but the encode still deadlocks. The decisive next step is a live
  15.1-vs-16.0 capture-log diff.
- **Diagnostics to strip before release** — `init.target.rc` still force-enables
  adb (`setprop sys.usb.config adb` in `on boot` + a `sys.usb.config=none`
  re-assert) and writes `/cache/nboot_*` boot tracers.
- **SELinux** — permissive (parked).
